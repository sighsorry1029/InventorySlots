# 공동 상자 GUI와 승인식 소유권 이전 검토

## 확인된 보고와 아직 확정하지 못한 원인

사용자 보고에서는 데디케이트 서버의 같은 로드 구역에 A가 먼저 도착하면 A는 상자 작업을 수행할 수 있지만, 나중에 도착한 B는 상자를 열어도 직접 이동·quickstack·restock이 되지 않았다. A가 떠나거나 B가 상자를 다시 지으면 B가 작업할 수 있었다. 커서가 사라지는 문제는 이전 수정 이후 재현되지 않았다고 보고했다. 내장 MultiUserChest를 끄면 작업이 가능했다.

이 차이는 상자 생성자 자체보다 현재 네트워크 소유자에 따라 실행 경로가 달라지는 상황과 일치한다. 다만 해당 A/B 환경에서 RPC 요청·응답과 실제 소유권·인벤토리 리비전을 함께 수집한 재현 결과가 없으므로, 특정 검증 조건이나 RPC 실패를 단일 원인으로 확정하지 않는다.

## 이번 구현의 경계

이전 MultiUserChest 구현은 보존 커밋 `8d39016f1c3ecbe750192ed0d1b36685efe79ec3`에 남아 있다. 이번 변경은 그 구현의 아이템 직렬화, 임시 보관, 영수증과 복구 프로토콜을 복원하는 작업이 아니다. 현재 주변 quickstack·restock에서 사용하는 승인식 소유권 이전을 GUI 상호작용에도 재사용한다.

- `ContainerAreaHandoffCore`는 요청 ID·상자 ID·작업 종류·예상 응답자를 확인한다. 승인 응답만으로 아이템을 변경하지 않으며, 현재 소유권·승인 토큰·저장된 인벤토리 상태가 모두 확인되어야 한 번 실행할 수 있다.
- `ContainerAreaOwnership`의 GUI 작업 경로는 상자 소유자의 승인을 받은 후 로컬 작업 콜백을 실행한다. 공동 GUI를 유지하더라도 같은 상자의 실제 변경은 짧은 소유권 사용 구간으로 직렬화한다.
- 사용자가 창을 닫거나, 접근 권한·거리·상자 상태가 바뀌거나, 상자가 언로드되거나, 요청 시간이 초과되면 확인되지 않은 작업을 실행하지 않는다. 늦게 도착한 응답이 취소된 작업을 다시 시작해서는 안 된다.
- 아이템 이동은 기존 인벤토리 이동 API와 슬롯·즐겨찾기·메타데이터 정책을 사용한다. 새로운 상자 저장 형식이나 플레이어 아이템 임시 보관 형식을 추가하지 않는다.

공동 GUI와 주변 작업은 서로 다른 사용 조건을 유지한다. 두 사람이 같은 창을 볼 수 있다는 사실이 두 사람에게 동시에 무조건 쓰기 권한을 부여한다는 뜻은 아니다. 외부 MultiUserChest가 설치된 경우에는 별도 모드의 GUI 및 소유권 경계를 유지한다.

다른 모드의 직접 인벤토리 수정과 제작 재료 소비 연동은 이번 구현·검증 범위에서 제외한다.

최종 검토에서는 생성자 지정 전 `Awake`가 상자를 영구 제외하지 않도록 구조만 캐시하고 플레이어 건설 여부를 다시 확인한다. 설정 전환은 기존 대기 작업·창·사용 상태를 정리한 뒤 실제 적용 상태를 바꾼다. 공동 상자의 스택 승인 응답은 새 작업을 시작하지 못하더라도 바닐라의 무승인 로컬 이동으로 넘어가지 않게 한다. 일반 주변 작업은 창을 닫은 뒤 남는 `InventoryGui.IsVisible()`의 프레임 지연 대신 Animator의 실제 표시 상태를 사용하며, 직접 GUI 작업은 계속 같은 열린 창을 요구한다. 이 네 경계를 기존 소스 계약 검사에 포함했다.

## 보존 범위와 한계

이번 범위는 실행 중 승인과 소유권 확인 없이 상자를 수정하지 않고, 같은 요청의 중복 실행을 막는 것이다. 플레이어 인벤토리와 상자 저장을 하나의 영속 트랜잭션으로 묶지는 않는다. 게임 프로세스 강제 종료, 서버 중단, 저장 실패 도중 두 저장소가 함께 복구되는 원자성은 바닐라 저장 체계와 별도로 검토해야 한다. 순수 상태 테스트 통과만으로 아이템 소실·복제가 모든 장애 상황에서 불가능하다고 보장하지 않는다.

이전 상자에 저장된 MultiUserChest 처리 기록을 삭제하거나 재해석하지 않는다. DLL을 교체하기 전에는 진행 중인 아이템 이동을 마치고 정상 종료한다. 서버와 모든 클라이언트를 같은 빌드로 교체한 뒤 다시 실행해야 한다. 이번 구현 작업에는 버전 증가·Release ZIP 생성·사이트 게시를 포함하지 않는다.

## 비공개 접근과 검증 상태

원본 Valheim 게임 DLL의 접근 제한을 기준으로 분석한다. 기존 프로젝트 전체의 publicizer 설정은 이번 변경으로 일괄 교체하지 않지만, 신규 소유권 경로의 비공개 멤버는 캐시된 Harmony `AccessTools` 접근자를 사용한다. 분석용으로 게임 원본을 publicize하지 않는다.

`build/CompatibilityCheck`는 원본 DLL을 로드하지 않고 Cecil 메타데이터로 직접 참조, Harmony 대상과 등록된 리플렉션 계약을 검사한다. 이 검사는 실제 Unity·Mono 접근 성공이나 다른 모드와의 패치 합성까지 검증하지 않는다. 신규 GUI 경로에서 추가된 비공개 접근도 최종 빌드의 실제 접근자와 원본 메타데이터를 대조해야 한다.

`InventorySlots.Tests`에는 기존 주변 작업 테스트 외에 `Interaction` 작업의 상태 테스트를 추가했다. 두 요청자 중 현재 소유권을 관측한 요청만 실행할 수 있는지, 승인과 상태가 다른 순서로 도착하는 경우, 잘못된 응답자·작업 종류, 중복·지연 응답, timeout·취소 이후 실행 방지를 확인한다. 또한 새 상태를 읽은 뒤 콜백을 실행하는 경계, 오래된 드래그 참조의 재검증, hold E의 단일 바닐라 콜백과 커서 대기 해제를 소스 계약 검사로 확인한다. 이는 입력한 네트워크 관측값과 호출 연결에 대한 검사이며, 실제 서버가 어떤 요청자에게 소유권을 부여하는지까지 재현한 테스트는 아니다. 빌드·자동 검사 결과는 해당 실행 로그로 확인하고, 아래 실제 멀티플레이 항목과 구분한다.

## 실제 게임 검증표

공통으로 작업 전후 A·B·상자의 아이템 합계와 아이템 품질·내구도·사용자 메타데이터를 비교한다. 재접속 후 저장 상태도 확인한다. 전용 서버에서 사용하는 게임·모드 빌드가 클라이언트와 맞는지 먼저 기록한다.

| 상황 | 확인할 결과 |
| --- | --- |
| 단독 플레이, 호스트, 데디케이트 서버 | 각 환경에서 설정 Off의 바닐라 단독 열기와 On의 공동 GUI를 각각 확인 |
| A가 먼저 도착, B가 나중에 도착 | B도 같은 상자에 대해 직접 이동·quickstack·restock 가능. 생성자에 따른 고정 권한 차이가 없어야 함 |
| B가 먼저 도착하거나 상자를 다시 건설 | 순서를 바꿔도 같은 결과. 현재 소유자 변경 후 기존 GUI가 오래된 아이템을 수정하지 않아야 함 |
| A·B가 같은 부분 스택을 동시에 가져오기 | 남은 수량 이상을 둘에게 지급하지 않음. 지연되거나 거절된 쪽은 최신 내용을 다시 확인 |
| A·B가 동시에 넣기·분할·교환·정렬 | 슬롯 좌표와 합계가 보존됨. GUI에 남은 오래된 선택이 다른 아이템에 적용되지 않음 |
| 열린 상자에 hold E 및 주변 quickstack·restock | 현재 상자도 대상에서 빠지지 않으며 같은 콜백·홀드 요청이 두 번 적용되지 않음 |
| 권한 없는 개인 상자·보호 구역·거리 이탈 | 창 표시와 별개로 변경 승인 거절. 이미 대기 중이던 작업도 실행 전 다시 확인 |
| 대기 중 GUI 닫기·사망·텔레포트·상자 파괴·언로드 | 작업 취소 후 아이템을 변경하지 않음. 늦은 응답으로 창이나 이동이 되살아나지 않음 |
| 응답 지연·중복, 승인 뒤 소유권 재변경 | 최신 소유권·토큰·인벤토리 상태가 확인되기 전 변경하지 않으며 재시도에 의한 중복 변경이 없음 |
| tombstone·선박·특수 컨테이너·외부 MultiUserChest | 기존 별도 정책과 모드 경계를 침범하지 않음 |

이 문서의 A/B 사례는 사용자 보고이며, 표의 네트워크·장애 시나리오는 실제 게임에서 추가로 확인해야 할 항목이다.
